# FE integration: two default QR links appear automatically

Shipped 2026-08-30. Additive — no endpoint, request, or response shape changed except one new field,
`autoGenerated`, on `QrLinkResponseDto`. Read this if your FE lists an event's QR links or renders
`GET /api/events/{eventId}/qr-links`.

## What changed

The moment an event activates (goes live/paid), the backend now mints two QR links for it
automatically, with no host action required:

- One `targetType: "EVENT_JOIN"` — the general invite.
- One `targetType: "MEDIA_UPLOAD"` — the gallery.

Both come back from `GET /api/events/{eventId}/qr-links` exactly like any other link, with one
addition:

```jsonc
{
  "id": "...",
  "targetType": "EVENT_JOIN",
  "publicUrl": "https://your-app/q/...",
  "maxGuests": 48,
  "autoGenerated": true,   // <-- new
  // ...
}
```

**Do this:** when `autoGenerated` is `true`, show something like "Set up for you" or a small badge
instead of implying the host configured this link. Everything else about it — repointing,
relabeling, revoking, editing `maxGuests` — works exactly like any other link via the existing
`PATCH`/`revoke`/`DELETE` endpoints documented in `qr-links-fe-integration.md`.

`maxGuests` on both defaults starts at the event's full remaining plan headroom (the plan's member
ceiling minus the host's own seat), the same clamp described in
`max-guests-plan-clamp-fe-integration.md`.

## What happens on a plan upgrade or downgrade

Only these two links' `maxGuests` automatically tracks the plan afterwards — re-clamped up on an
upgrade, down (never below 1) on a downgrade or a reversed upgrade. Any link the host created
themselves, or edited the guest limit on (including one of these two, once edited), is **not**
touched by this — it keeps whatever the host set, and real overflow is still caught at join time
the same way it always was (`5009`/`5035`, unchanged).

This resync runs asynchronously, shortly after the plan change — do not assume `maxGuests` on these
two links is already updated in the very next response after an upgrade completes; a page showing
QR-link stats should tolerate a brief window where the number hasn't moved yet, the same way it
already tolerates polling `/qr-links/stats` for freshness.

## What did not change

- No new endpoint. No change to `POST /api/qr-links`, `PATCH /api/qr-links/{id}`, or any invite
  onboarding endpoint.
- A host can still delete or revoke either default link. Nothing recreates it — revoked means
  revoked, same as any other link.
- Personalised, per-recipient invitations (`POST /api/event-invitations`) are entirely unaffected.
- Events that were already `ACTIVE` before this shipped do not retroactively get these two links —
  this only applies going forward, from the next activation or plan change.
